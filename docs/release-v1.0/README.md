## PayMongo dates, risks and protective decision

The owner supplied the full merchant notice during this audit. Its account-specific schedule is:

- **1 December 2026:** live API keys rotate; Individual wallets/payout arrangements become closed-loop; non-QR Ph methods and Storefront/Pages are restricted. Stale Worker credentials may then prevent canonical retrieval as well as creation. QR Ph remaining available does not establish continued API access.
- **29 January 2027, 11:59 PM PHT:** notice's deadline for existing Individual accounts to upgrade before disablement. This is distinct from December 1 and from the 30-day rule for newly activated accounts.

The [current general provider guide](https://docs.paymongo.com/docs/account-settings-doing-business-in-the-philippines#individual-accounts-30-days-to-register) describes registration windows and account categories; it does not reproduce the notice's January date/key-rotation schedule and includes a November 27 activation-scope section. Treat the owner's notice as the supplied merchant advisory; account applicability and any changed terms still need Dashboard/support confirmation. The [business-type guide](https://docs.paymongo.com/docs/account-settings-business-types#upgrading-your-business-type) documents the upgrade path, but implementing manual acknowledgment is not a claim of exemption from receiving-account/provider requirements.

**Before December 1:** owner must inspect the actual PayMongo account type, wallet balance, payouts, refunds/disputes and restrictions; privately export provider ledger/settlement records while accessible and resolve any financial decisions personally. D1 exports preserve application facts but cannot supply a missing provider payout ledger. No transfer, withdrawal, account upgrade, credential revocation or financial-status mutation was performed. Dashboard sign-in was required; saved-login browser access could not be completed, and connected Gmail searches returned no notice. The notice was supplied directly instead.

Keep LIVE events inactive. There is no safe checkout-only environment switch today; add it as Phase 2 priority zero with legacy retrieval/webhook/claim/report tests. Event pause/end is an existing narrower control if any event is later found active. Never turn the combined LIVE flag off as a substitute, remove keys, stop Cron or delete data merely to claim retirement. If provider access later fails, retain UNKNOWN/review evidence and already authorized rights; do not infer unpaid/settled.

## Storage, recovery and security assessment

Critical print/checkout writes fail closed; `AppRecoveryStore.loadChecked` distinguishes a damaged original from no checkpoint. `EventOperationalState.refresh` exposes that error. Print intent persists before bytes; launch normalization makes an interrupted send uncertain. Outbox pruning protects whole uncertain/pending batches. Parked guest assets and exact acknowledgment identity survive relaunch. These implemented safeguards must remain authoritative.

`RecentSessionArchiveStore` has explicit management/tombstones and a `prune` helper with 7-day/250-count constants, but no production invocation of that helper was found; this is **not** evidence of an active automatic seven-day retention policy. Pending galleries are cleared only after public verification and durable proof in the service. Storage readiness is displayed and critical archive/write errors block printing; venue exhaustion/replacement restoration still needs qualification. No bulk cleanup was run.

Recovery state, pending galleries, archives, artwork and print journal apply backup exclusion; several credentials/PINs are ThisDeviceOnly. Consequently iCloud/device migration cannot be assumed to restore an operable booth. Design an authenticated, encrypted portable backup with checksums and nonprinting restore mode; provision fresh device credentials through the owner, and reconcile original fulfillment before enabling a replacement. Preserve old identities and uncertain copies, rather than minting new print rights.

The repository is public. Pattern scanning examined **2,909 unique reachable Git blobs** (~344 MB) for PayMongo secret keys, GitHub tokens, Google API keys, private-key PEM blocks and Telegram bot tokens; no matches were found. This is a bounded pattern check, not proof that no credential/private material has ever existed. New documentation contains no receiving-account details, customer gallery tokens/media, financial amounts/record IDs or credentials. Private exports/settings/source captures remain outside Git. No history rewrite or visibility change was made.

Project deployment target is iOS 18.0; current marketing/build values are **1.0 / 3**, not the requested final **1.0.0**. Change version/build only when preparing the complete candidate. The matching local profile is Personal Team development provisioning. Apple documents [seven-day Personal Team profiles](https://developer.apple.com/help/account/basics/about-your-developer-account); renewal is a temporary development option, not sustainable unattended distribution. With an eligible existing paid **individual** membership, registered-device development/ad hoc distribution is the practical private-device option ([ad hoc profiles](https://developer.apple.com/help/account/provisioning-profiles/create-an-ad-hoc-provisioning-profile)); inspect actual expiry and app/Keychain compatibility. Individual [enrollment](https://developer.apple.com/help/account/membership/program-enrollment/) is possible, but no current paid membership or distribution certificate/profile was established here. Owner chooses membership/distribution; no purchase or team change is authorized by this report. TestFlight is beta distribution with [90-day build availability](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/), not a permanent install.

Sequence: permanent legacy archive → complete main implementation → signed **1.0.0** / unique build → **v1.0.0-rc.1** → qualify that exact binary on Carlo → **v1.0.0**. Do not mint candidate/stable tags during Phase 1. Reuse the qualified candidate binary if no corrective source change is required.
